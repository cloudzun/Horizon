<h2 class="news-title"><a href="https://openai.com/index/gpt-6-for-everyone/">OpenAI 发布 GPT-6 及面向所有用户的 Intelligent UI</a><span class="score-badge score-high">9.0</span></h2>
<div class="news-meta"><span class="source-chip chip-hackernews">hackernews</span><span class="source-name">joshuawright11</span><span class="news-time">Oct 7, 18:00</span></div>
<p class="news-summary">OpenAI 发布了 GPT-6 以及配套的 “Intelligent UI”，并率先在 ChatGPT 的 Chat 标签页面向 Plus、Pro、Business 和 Enterprise 套餐全球推送，Free 与 Go 套餐将在次日跟进。此次发布还附带了系统卡（system card），其中提及了 GPT-6 Sol 和 GPT-6 Luna 等模型版本。 OpenAI 此次不只是更新模型，而是把新模型与重新设计的界面一起发布，这意味着它正推动生成式 AI 成为日常软件的默认层，可能改变庞大用户群体与 AI 的日常交互方式。附带的安全文档也让评测指标退步的问题直接进入了公众对本次发布的讨论之中。 根据发布公告中附带、并被社区成员引用的系统卡，GPT-6 Sol（October）在标准自残评测上出现统计显著的退步，GPT-6 Luna（October）则在标准自残、血腥内容和性内容上出现显著退步，此外还在极端主义视觉评测中有所退步。评论者还批评了界面中的大量留白和清单式布局等设计选择。</p>
<div class="news-background"><strong>背景</strong> GPT-6 是 OpenAI 生成式预训练 Transformer（GPT）大语言模型系列中的第六个主要版本，接续 GPT-5 系列，而 “Sol” 和 “Luna” 看起来是该系列中的具体模型变体。“智能用户界面”（intelligent UI）指的是融入了人工智能能力的用户界面，区别于传统的固定式界面。OpenAI 通常在发布模型时同步发布“系统卡”，用于记录安全评测、已知局限和基准表现。</div>

<h2 class="news-title"><a href="https://openai.com/index/sharing-ai-progress-in-mathematics/">OpenAI 发布 AI 生成的数学预印本，引发热议</a><span class="score-badge score-high">9.0</span></h2>
<div class="news-meta"><span class="source-chip chip-hackernews">hackernews</span><span class="source-name">OfficialTurkey</span><span class="news-time">Oct 6, 22:17</span></div>
<p class="news-summary">OpenAI 在 github.com/openai/math 上发布了一个 GitHub 仓库，其中包含一个存放 AI 生成数学预印本的目录。根据社区评论，这些预印本声称解决了包括 Unique Games Conjecture（唯一游戏猜想）和 Barnette&#x27;s Conjecture（巴内特猜想）在内的多个重大未解问题，但这些具体说法在此并未得到独立验证。 如果这些声称的结果成立，AI 生成的对长期未解问题的证明将成为 AI 能力和数学研究实践的双重范式转变。尤其是 Unique Games Conjecture 的证明将重塑近似困难性理论，社区评论者指出这可能迫使相关教科书被重写。 直接提供的证据仅包括仓库链接和社区讨论，因此在专家审阅这些预印本之前，相关证明主张应被视为未经证实。评论者还提到一篇媒体报道，描述研究人员正抢在 AI 之前完成 Unique Games 的证明，这表明该议题存在争议且仍在快速演变。</p>
<div class="news-background"><strong>背景</strong> Unique Games Conjecture 由 Subhash Khot 于 2002 年提出，是计算复杂性理论中的一个猜想，它断言确定某类约束满足“游戏”的近似值是 NP 困难的，对近似困难性有广泛影响。Barnette&#x27;s Conjecture 是一个未解决的图论问题，它断言每个每个顶点有三条边的二分多面体图都具有哈密顿回路。两者都属于自动定理证明的范畴——这是自动推理的一个子领域，研究由计算机程序证明数学定理，通常还需要借助 Lean 等证明助手与人类数学家协作。</div>

<h2 class="news-title"><a href="https://www.anthropic.com/claude-haiku-5-5">Anthropic 发布 Claude Haiku 5.5，采用分层定价并向订阅用户发放 API 额度</a><span class="score-badge score-mid">8.0</span></h2>
<div class="news-meta"><span class="source-chip chip-hackernews">hackernews</span><span class="source-name">sfkgtbor</span><span class="news-time">Oct 7, 18:01</span></div>
<p class="news-summary">Anthropic 发布了新的小型模型 Claude Haiku 5.5，其 API 定价采用两档结构：提示词在 100,000 token 以内时，输入为 $0.10 / 百万 token、输出为 $0.50 / 百万 token；超过该阈值后分别上涨至 $0.50 和 $2.50。与此同时，Anthropic 表示将向 Max 和 Team 订阅用户按月发放 API 额度——Max 5x 用户每月 $100，Max 20x 用户每月 $200，Team 订阅用户最多可获得 $500 并在成员间共享。 这条消息之所以重要，是因为 Haiku 是 Anthropic 主打便宜、快速的模型层级，其价格与延迟的变动会直接影响开发者在生产环境中的取舍，尤其是高并发的 Agent 工作负载。新增的订阅 API 额度也模糊了聊天订阅与付费 API 使用之间的界限，让 Max 和 Team 个人用户每月拥有一定预算，无需单独结算即可上线基于 API 的功能。 评论者关注两个不寻常的细节：触发更高价档的 100,000 token 门槛只适用于 Haiku，而不适用于 Sonnet 或 Opus；社区测试还显示成本与性能提升明显——一项基准测试报告 Haiku 5.5 比 Haiku 4.5 便宜约 9 倍，准确率高出约两个字母等级；另一项跨 thinking level 的 SVG 生成测试发现，&#x27;low&#x27; 档画出的自行车车架是错误的，而 medium 到 max 档都能正确渲染，其中 max 档耗时 5 分 9 秒、花费 3.3826 美分，而 low 档仅用 7 秒、花费 0.0936 美分。</p>
<div class="news-background"><strong>背景</strong> Anthropic 的 Claude 系列按层级划分：Haiku 定位为最小、最快、最便宜的模型，Sonnet 和 Opus 则是体量更大、能力更强（也更贵）的同门模型。API 定价通常按每百万 token 报价，模型还可以用不同的 reasoning effort 或 &#x27;thinking&#x27; 档位运行，以额外算力和延迟换取更好的答案。Agent 工作负载对按 token 计费尤其敏感，因为它们会反复把累积的上下文送回模型，上下文长度很容易远超一次简单提示词。此次新额度接入了 Anthropic 已有的 Max 和 Team 订阅计划，而这些计划此前覆盖的是聊天和 Claude Code 使用，而非直接的 API 调用。</div>

<h2 class="news-title"><a href="https://news.mit.edu/2026/margaret-hamilton-computing-pioneer-dies-1007">阿波罗飞控软件先驱 Margaret Hamilton 逝世，享年 88 岁</a><span class="score-badge score-mid">8.0</span></h2>
<div class="news-meta"><span class="source-chip chip-hackernews">hackernews</span><span class="source-name">Lobsters</span><span class="news-time">Oct 7, 21:16</span></div>
<p class="news-summary">据 MIT News 报道，计算领域先驱 Margaret Hamilton 逝世，享年 88 岁。她曾在 MIT Instrumentation Laboratory 领导阿波罗飞船机载飞行软件的开发。她的去世在 Hacker News 上引发了大规模的悼念讨论（452 分、44 条评论），内容包括致敬、个人回忆以及对一手资料的指路。 Hamilton 是软件工程史上的奠基性人物：她的团队为阿波罗飞行软件设计的错误检测与恢复机制，被普遍认为在阿波罗 11 号登月过程中帮助避免了任务中止。她也被普遍认为推广了“software engineer（软件工程师）”这一称谓，从而推动软件开发成为一门被认可的工程学科，而不再只是硬件工作的附属。 这套软件运行在阿波罗导航计算机（AGC）上。AGC 采用 16 位字长（15 个数据位加 1 个奇偶校验位），约有 4,100 个硅集成电路封装，内存仅约 32KB，其中大部分存储在手工业者编织的 core rope memory（磁芯 rope 存储器）中。宇航员通过 DSKY（显示与键盘）单元与它交互；AGC 由 MIT Instrumentation Laboratory 为阿波罗计划研制，于 1966 年首次飞行。</p>
<div class="news-background"><strong>背景</strong> 阿波罗导航计算机是安装在每一艘阿波罗指令舱和登月舱上的机载计算机，为飞船的制导、导航与控制提供计算和电子接口。它是第一台基于硅集成电路的计算机，尽管内存极小，性能却可与 1970 年代初的家用电脑相比。由于每艘飞船只搭载一台这样的计算机，可靠性与故障恢复成为关键的设计考量。Hamilton 在 MIT Instrumentation Laboratory（即今天 Draper Laboratory 的前身）工作，在那里领导团队编写机载飞行软件——这些代码必须一次性正确运行，不可能远程打补丁。</div>

<p class="news-summary">一篇新发布在 arXiv 上的论文（题为 &quot;Navier–Stokes Lost in Translation&quot;）指称，某个关于 Navier–Stokes 方程爆破（blow-up）证明的 Lean 形式化结果，与其声称所形式化的自然语言证明并不对应。该指控引发了争论：LLM 辅助的形式化验证究竟是否真正证明了它所宣称的结果。 如果这一批评成立，就会削弱「LLM 把自然语言证明翻译成 Lean 即等于继承了原论证有效性」的观念，而这直接影响人们对 AI 辅助数学形式化成果的信任程度。它也凸显出：形式化验证保证的是所写下的那个命题本身，而非其背后的非正式意图。 从讨论来看，论文针对的是自然语言证明与 Lean 形式化之间的等价性或忠实性，而不是 Lean 证明本身的内部正确性。评论者指出，因此关键问题在于该 Lean 定理是否等价于 Clay 研究所发布的原始问题陈述，因为精确地陈述一个问题有时与证明它同样困难。</p>

<p class="news-summary">一个名为 PhotoCraft 的开源项目发布了对 Adobe Photoshop 的洁净室重实现，完全用纯 Rust 编写，提供图层、蒙版、调整图层、图层样式、文字、矢量与画笔功能，是一个支持真实 PSD 读写、可离线运行的原生应用。其仓库称，重新保存文档时，psd-tools 测试集中 309 个文件里有 307 个渲染结果保持一致，混杂 ag-psd/psd-tools 测试集的 170 个文件中有 169 个保持一致；而独立的 photocraft-psd crate 对所有可解析的语料文件都能逐字节复现。 Photoshop 的图层文档格式深深嵌入专业创意工作流，却由单一厂商掌控，因此一个具备真实 PSD 兼容性的 Rust 原生实现，为开源图像编辑社区与 Rust 生态提供了新的参照，可用于构建与既有图层文档互操作的工具。项目还强调 UI、CLI、JSON 控制通道与 MCP 服务器共享同一套命令注册表，这意味着脚本和 AI agent 可以直接驱动图像编辑工作流——随着 agent 工具普及，这一模式正变得愈发重要。 项目明确说明，重新保存的文件与原文件并非逐字节相同，因为 PhotoCraft 会重写图像资源、图层记录和合成图像；而尚未建模的内容（如原始数据块、描述符和扩展数据）会被保留而非丢弃。项目还提到一个“合成预言机”（composite oracle），将其自身渲染结果与 Photoshop 导出的合并图像对比，覆盖渐变插值模式（Classic、Perceptual、Linear）、图层效果、形状描边、剪贴和填充不透明度；此外支持 PSB、16/32 位文档以及 CMYK 和 Lab，所有菜单项、工具与对话框都由 500 多条命令驱动。</p>

<p class="news-summary">Docker 在 GitHub 上开源了名为 docker-agent 的项目，官方描述它是一个用于在容器化环境中构建和运行协作式 AI Agent 的工具，并以「无需写代码（no code required）」作为卖点。该消息在 Hacker News 上引发了大量关注，帖子获得约 165 分和 77 条评论。 Docker 是重要的基础设施厂商，其容器工具早已深度嵌入开发者工作流，因此它进军 AI Agent 编排领域，可能推动 Agent 的打包、隔离与可复现方式走向标准化。这一点之所以重要，是因为 agent harness（Agent 运行框架）领域已经挤满了相互竞争的框架，而容器原生的编排方案对那些更看重安全性与可复现性、而非又一层抽象封装的团队可能更有吸引力。 目前可获得的公开信息仅限于项目自己的一句话描述以及 HN 上的讨论，因此诸如它支持哪些模型或运行时、能协作多少 Agent、采用何种许可证以及成熟度如何等具体能力均尚待核实。尤其是「无需写代码」这一说法受到了评论者的质疑，因此读者应把项目的定位视为宣传口径，而非经过验证的技术保证。</p>

<p class="news-summary">在 2026 年 10 月 6 日的一篇文章中，Simon Willison 指出 EmbeddingGemma 2 采用 Apache 2.0 许可证意义重大，因为它为用户摆脱封闭的纯托管嵌入模型提供了一条退路。他强调，嵌入模型的典型用法是计算并存储成千上万甚至数百万条向量，因此一旦厂商停用某个专有模型，用户就得自掏腰包把已经存好的全部内容重新嵌入一遍。 这是一种关于许可证与锁定风险的论证，而非性能榜单之争：在宽松许可证下开放权重，意味着开发者可以先采用托管嵌入 API，同时保留日后自行部署或更换供应商的选择权。这呼应了 AI 生态中一个更广泛的担忧——专有且纯托管的模型会给任何建立在大量已存储向量之上的应用带来隐性迁移成本。 Willison 明确表示他并不想自己托管模型，更愿意付费使用供应商提供的服务，同时知道开放权重版本可以作为后备方案；他还提到 OpenAI 在 2024 年 4 月曾承诺承担用户用新模型重新嵌入内容的费用，以此说明这类保证并非每家供应商都会给出。根据搜索结果，EmbeddingGemma 2 是一个拥有 7.4 亿参数的多模态嵌入模型，基于 Gemma 4 架构构建，原生支持 768 维表示，并可通过 Matryoshka Representation Learning（MRL）截断到 128、256 和 512 维后重新归一化。</p>
<div class="news-background"><strong>背景</strong> 嵌入模型把文本、图像等内容转换成数值向量，使软件能够按相似度进行比较，这是搜索、检索增强生成（RAG）、推荐和聚类系统的基础。由于这些向量通常只需计算一次并存入数据库，更换嵌入模型往往意味着要重新计算全部已存储向量，在规模较大时这项工作效率低且成本高。Apache 2.0 是一种宽松的开源许可证，允许商业使用和修改，且不要求公开衍生作品，因此常被拿来与限制更多或仅供托管的模型条款作对比。</div>

<h2 class="news-title"><a href="https://hexrat.cc/pages/blog/2026_10_07">rat 后端用 584 行装箱式寄存器分配器取代线性扫描</a><span class="score-badge score-mid">7.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Oct 7, 18:01</span></div>
<p class="news-summary">在 2026 年 10 月 7 日的一篇博客文章中，rat（一个带有半可用 C99 前端的小型编译器后端）的作者描述了如何用优先级装箱式分配器取代旧的线性扫描寄存器分配器。新分配器从 1392 行缩减到 584 行，不再按程序顺序而是按重要性（溢出权重）遍历活跃区间，作者称它与 LLVM 的 greedy 分配器同属一类，只是去掉了大部分难点，同时生成的代码更好。 它具体地证明了一个实用的寄存器分配器不必是一堆不断打补丁堆出来的庞大机器：作者通过度量旧分配器中哪些部分真正起作用，删掉了约 800 行代码，反而生成更好的代码。对于编写小型语言后端、JIT 或把编译器基础设施移植到受限环境的人来说，这是一个有价值的参考案例。 该分配器把虚拟寄存器映射到通用寄存器（可用 12 个）或 xmm 寄存器（Linux 上 14 个，但 Windows 上只有 xmm0–xmm3 可用，xmm4/xmm5 用作溢出临时寄存器），没有空闲寄存器时则映射到栈槽；活跃性用位掩码跟踪，每 64 个槽位配一个汇总掩码，使较长的活跃区间可以一次跳过 64 个槽位。复制合并（coalescing）会把同类寄存器且活跃区间不重叠的虚拟寄存器合并成一个 bundle，rat 按循环深度对复制候选排序，让热点复制先合并，避免被冷复制抢先阻断。</p>
<div class="news-background"><strong>背景</strong> 编译器会把源代码下降为一种假装拥有无限多虚拟寄存器的中间表示（IR），但目标 CPU 只有少量固定的物理寄存器，因此寄存器分配器必须决定哪些值放在寄存器里、哪些溢出（spill）到内存——每次溢出都意味着一次存储加一次加载。寻找最优分配是 NP-hard 问题（至少和图着色一样难），所以实用的分配器都使用启发式方法，通常围绕“活跃区间”（live range）来组织，即一个值从被写入到最后一次被读取的区间，因为两个值只有在活跃期不重叠时才能共用同一个寄存器。经典的线性扫描分配器按程序顺序遍历活跃区间，而 greedy / 优先级类分配器则按重要性给区间排序，把每个区间放进第一个能容纳它的寄存器；复制合并（coalescing）是与之配套的技巧，把由复制指令相连的区间合并起来，从而删掉这条复制。</div>

<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Oct 7, 16:22</span></div>
<p class="news-summary">00f.net 上的一篇博客文章作为 zeroization 系列的第一篇，指出盲目为密钥数据添加内存擦除函数调用并不可靠，甚至可能让情况变得更糟。作者借助 Godbolt 示例说明：对局部中间变量调用 memset() 会被编译器完全优化掉（加与不加生成的指令完全相同），并展示在某些情况下加入擦除操作反而会制造出原本不存在的栈上副本。 Zeroization 是被广泛推荐的安全卫生实践，开源项目经常收到为任何看起来像密钥的数据添加擦除调用的 PR，因此这种细致的批评对当前把此类补丁视为唾手可得的安全收益的安全工程师和系统工程师而言很有意义。如果朴素擦除在常见构建配置下适得其反，就会同时影响这类补丁的审查方式，以及开发者对自己在内存中密钥生命周期保障的认知。 作者指出，死存储消除（dead store elimination）会删除之后不再被读取的写入；取一个值的地址可能强制产生新的栈副本（擦除清掉的是该副本，寄存器中的副本依然存在）；链接时优化（LTO）使“把实现藏到另一个文件”的做法基本失效；寄存器会出现在 core dump、休眠文件和 VM 快照中，还可能通过 Zenbleed 这类微架构缺陷泄露，且单个 SIMD 寄存器就可能装下完整的 256 位密钥甚至 512 位哈希。作者的建议不是停止擦除本来就存在于内存中的密码缓冲区、密钥调度或上下文，而是在为小型局部变量添加擦除之前，检查你实际发布的优化构建，包括 LTO 和 hardening 标志。</p>
<div class="news-background"><strong>背景</strong> Zeroization（零化）是 FIPS 140 等标准中使用的术语，NIST 的 CSRC 术语表将其定义为：在密钥或秘密数据被销毁后，其值的任何信息都无法被恢复。它指在秘密数据不再需要时，主动覆写内存中的密钥、密码、明文缓冲区等内容。编译器通常会进行死存储消除（dead store elimination）优化，删除那些其值之后不再被读取的内存写入；从编译器的角度看，在密钥离开作用域前将其置零的赋值就是一个死存储，因此擦除代码可能直接消失。链接时优化（LTO，又称过程间优化或模块间优化）会把这种分析扩展到链接阶段的多个编译单元之间，这正是把擦除代码挪到另一个文件也未必能躲过优化器的原因。</div>

<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Oct 6, 21:12</span></div>
<p class="news-summary">Mitchell Hashimoto 发布了一份关于 OSC 7501（Program Status Protocol，程序状态协议）的规范，这是一种新的终端转义序列，允许任何程序向终端报告自己正在做什么——idle（空闲）、working（工作中）、blocked（等待用户输入）、finished（完成）或 failed（失败），并附带原因。文中给出了一个具体示例：Terraform 发出 blocked/permission 状态，并携带 base64 编码的消息 “Apply 3 to add, 1 to change, 0 to destroy?”，终端或任何其他工具随后可以以通知、收件箱条目或状态图标等形式呈现这一信息。 目前，想要判断一个长时间运行的程序是忙碌、等待还是已完成，工具只能靠抓取屏幕内容或解析窗口标题来猜测，这种方式很脆弱且需要不断更新。统一的、终端原生的协议可以让真正了解自身状态的程序直接上报状态，从而改善构建、部署尤其是编码代理（coding agent）场景下的互操作性——不过这仍是一份早期规范提案，尚未成为被广泛采用的标准。 该协议有意只负责共享状态，把全部呈现方式交给终端决定；Hashimoto 表示他已经实现过两次（分别在 libghostty 和 Rex 中），并在 Terraform、Claude Code、Codex 和 Homebrew 中做了概念验证集成，每处实现都不超过十几行代码。规范文本还涉及检测、terminfo、大小限制和安全性等边界问题，Hashimoto 也提到他与许多终端程序和终端模拟器的维护者保持联系，他们参与了评审并帮助完善了这份规范。</p>
<div class="news-background"><strong>背景</strong> 终端程序通过 ANSI 转义序列与终端模拟器通信，其中名为 OSC（Operating System Command，操作系统命令）的一类序列早已用于带外信号传递，例如 OSC 7 可以在 WezTerm 等应用中告知终端当前工作目录。由于此前不存在用于程序状态的这类序列，现有工具只能依赖启发式猜测：像 Claude Code 这样的交互式编码代理会通过在窗口标题中放置盲文（Braille）旋转字符来表示自己正在“工作”（自 2.1.228 版本起改用半圆旋转字符），而收件箱工具 Herdr 则维护了 16 条 TOML 规则来把代理归类为 idle、working 或 blocked。文中指出，仅针对 Claude Code 的规则文件在三个月内就修改了十次，这正说明了这种猜测方式的脆弱性，也正是希望给程序提供一种标准化状态上报方式的动因。</div>

<h2 class="news-title"><a href="https://andersmurphy.com/2026/09/29/faster-streaming-html-with-batches-and-aggregates.html">用批处理与聚合加速流式 HTML</a><span class="score-badge score-mid">7.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Oct 7, 09:26</span></div>
<p class="news-summary">Anders Murphy 发布了一篇博客，讲解如何通过把每个 tick 视为一个批次、并对所有用户的帧做聚合式的「内容寻址组件缓存」来加速服务端流式 HTML。他报告称，实验性项目 hyperlith 已在生产环境运行，在一台 2 vCore 共享 VPS 上大致可支撑 1000 个并发用户、10 FPS，并附上了 4000 并发用户过载测试在加入缓存前后的火焰图对比。 这篇文章表明，服务端驱动、immediate mode 的 HTML 架构无需客户端视图层就能扩展到相当规模的实时负载，这对在 hypermedia 框架与重度 JavaScript 单页应用之间做取舍的开发者很有参考价值。其核心洞见——以 tick 为边界做批处理，可把可能呈二次方增长的渲染工作量（用户数 × 操作数）变成线性规模（每个 tick 一组渲染）——是一套适用于任何服务端流式 UI 的简单心智模型。 文中描述的系统通过长生命周期的 SSE 连接，配合 Brotli 或 Zstandard 流式压缩，把每个新帧推送给所有已连接客户端，并用一个简单的 Clojure hiccup 解释器递归写入字节缓冲区。作者特别指出的一个限制是它与 WTinyLFU 缓存的相互作用：如果包裹组件一直在变，它永远无法通过准入机制进入缓存；而如果包裹组件保持稳定，被缓存的子组件又会因为长期不被请求而被淘汰，同时缓存子组件和父组件会让缓存占用空间大致翻倍。</p>
<div class="news-background"><strong>背景</strong> 这里的流式 HTML 指的是一种服务端驱动的渲染风格（有时称为 immediate mode）：几乎所有状态都放在服务端，每个 tick 重新渲染页面并把生成的 HTML 推送给客户端，而不是在浏览器中维护一套视图层。文中提到的 Datastar 是一个轻量的 JavaScript hypermedia 框架，它把类似 HTMX 的、基于 SSE 的服务端更新与客户端响应式信号结合起来，作者提到自己参与了它的 Discord 社区。示例代码使用 Clojure，并采用 hiccup——一种把 HTML 表示为嵌套向量的 Clojure DSL；火焰图则由 clj-async-profiler 生成，这是一个可嵌入 Clojure 应用的高精度性能分析器。</div>
