<p class="news-summary">谷歌 DeepMind 的 WeatherNext AI 模型在热带气旋预报上取得突破，将预警提前量延长了最多 24 小时。该模型现已开源，供全球研究人员使用。 WeatherNext 在推理效率上比传统数值天气预报（NWP）模型高出几个数量级，同时预报能力更优。多一天的预警可以挽救生命、减少损失，而开源模型则有助于更广泛的应用和进一步研究。 该模型采用机器学习方法，很可能基于多尺度分层图神经网络，而非经典的基于物理的模拟。与现有方法相比，它能为气旋预警提供额外一天的提前量。</p>

<h2 class="news-title"><a href="https://blog.rust-lang.org/2026/08/04/enabling-polonius-alpha-on-nightly/">在 nightly 启用下一代借用检查器 Polonius Alpha</a><span class="score-badge score-high">9.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Aug 8, 15:34</span></div>
<p class="news-summary">Rust 团队已在 nightly 频道启用下一代借用检查器 Polonius Alpha，并计划在年底前将其稳定。这源于多年来对 Polonius 方案的研究与开发。 Polonius Alpha 为借用检查器引入了流敏感分析，使更多当前基于 NLL 的检查会拒绝的安全 Rust 代码能够通过编译。一旦稳定，这将成为 Rust 借用检查器的重要里程碑，并使所有 Rust 开发者受益。 Polonius Alpha 是流敏感的，而当前的 NLL 实现是流不敏感的，因此它能接受某些分支中借用不活跃的代码。但它并非旧 Polonius 实现的严格超集，有些在旧 Polonius 下能编译的程序在 Polonius Alpha 下无法编译。性能总体可接受，但仍存在一些回归，用户可通过 -Zpolonius=off 禁用。</p>
<div class="news-background"><strong>背景</strong> Rust 的借用检查器经历了从基于 AST 的原始检查器到非词法生命周期（NLL）的演进，NLL 于 2022 年在 Rust 1.63 中完全稳定。Polonius 得名于莎士比亚《哈姆雷特》中的人物，是一个研究项目，旨在用更精确的流敏感分析来建模借用检查。这个新版本被称为 Polonius Alpha，它最大程度地减少了对现有 NLL 实现的重构，同时扩展了可编译代码的范围。</div>

<h2 class="news-title"><a href="https://github.com/xoreaxeaxeax/rosenbridge">Rosenbridge 项目再掀 x86 CPU “后门” 争议</a><span class="score-badge score-mid">8.0</span></h2>
<div class="news-meta"><span class="source-chip chip-hackernews">hackernews</span><span class="source-name">epestr</span><span class="news-time">Aug 8, 07:04</span></div>
<p class="news-summary">Hacker News 上的一则讨论重新审视了 Rosenbridge 项目，该项目记录了某些 x86 处理器中的一个硬件后门。评论者反驳说，这个所谓的后门实际上是 CPU 的文档化特性，而非隐藏的恶意能力。 这场争论凸显了人们对闭源 CPU 厂商日益增长的不信任，尤其是针对政府要求植入的后门以及 Intel ME 和 AMD PSP 等无法验证的组件。这也强化了以 FPGA 等开源硬件作为更可信替代方案的呼声。 Rosenbridge 后门据称影响部分 x86 桌面、笔记本和嵌入式处理器，允许 ring 3（用户态）代码绕过处理器保护。有评论者称，受影响的只是几十年前的 VIA C3 嵌入式 x86 芯片，且相关白皮书因涉及学术不端而无法发表。</p>
<div class="news-background"><strong>背景</strong> 硬件后门是指在计算机物理部件中实现的隐藏漏洞，可能被用于未经授权的访问或监控。Rosenbridge 由安全研究员 Christopher Domas 创建，记录了某些 x86 处理器中的此类后门。x86 CPU 使用特权环（ring）机制，其中 ring 3 是最低权限的用户态；Rosenbridge 的发现声称即使是 ring 3 代码也能利用该后门获取更高权限。</div>

<p class="news-summary">美国能源部（DOE）启动了 Genesis 开放模型计划，旨在创建一类新的开放权重基础模型以加速科学发现，并正在向商业、学术和研究机构征集意见。该计划是 DOE 更广泛的 Genesis 任务的一部分。 该计划填补了美国开放权重模型领域的显著空白，尤其是在 Llama 系列被弃用之后。它为开放模型提供了一条获得政府认可的路径，避免国家安全顾虑，并可能加强美国在科学 AI 领域的领导地位，同时为 DeepSeek 等国际模型提供了替代方案。 该计划瞄准材料发现、能源系统、地球系统建模、聚变、生物学和高能物理等科学领域。值得注意的是，官方描述中提及的是“基础模型”而非“大语言模型”，这表明其范围可能超出语言模型，涵盖其他架构和数据类型。</p>

<p class="news-summary">Christopher Domas 在 GitHub 上发布了“Assembly Hall of Shame”，这是一个比赛哪条 x86 指令执行最慢的排行榜。目前的冠军是 AMD Ryzen 7 5800H 上的 fxrstor64，它通过从高延迟 MMIO 区域加载 FPU/MMX/XMM 状态，同时用大量 hammer 核以非 posted 事务打满 PCIe 结构，拿到了 198,002,498,236 个周期（62 秒）的成绩。 该项目颠覆了通常的性能优化思路，系统性地测绘现代 x86 CPU 上单条指令的最坏情况延迟。这些病态时序技术对底层系统编程和安全研究很有意义——Domas 此前曾用类似的慢指令技巧攻破 System Management Mode（SMM）。 比赛规则要求只对单条指令计时，禁止可中断指令，不得计入陷阱/模拟处理时间，且硬件必须为出厂默认配置。进行中的挑战打算利用 xrstor64 配合 Intel AMX 状态（约 8KB，而 fxrstor64 仅为 512 字节），把成绩推向约 1,000,000,000,000 个周期。</p>
<div class="news-background"><strong>背景</strong> 在 x86-64 中，FXRSTOR64 从 512 字节的内存区域恢复 x87 FPU、MMX、XMM 和 MXCSR 状态，对应的 FXSAVE64 则保存这些状态。MMIO（内存映射 I/O）让 CPU 通过读写地址来访问 PCIe 设备寄存器，这些地址会经过 PCIe 结构路由到设备，一旦结构被饱和，事务可能停滞很长时间。Intel AMX 是较新的面向矩阵运算的 x86 扩展，它新增了 tile 寄存器，使保存的状态显著变大。这些概念构成了该项目寻找最慢指令实验的基础。</div>

<div class="news-background"><strong>背景</strong> Blue Pill 是一款基于 ARM Cortex-M3 STM32F103C8 微控制器的廉价开发板。与带有 TrustZone 的较新 Arm 内核不同，Cortex-M3 没有 MMU 或硬件安全扩展，因此隔离必须依靠 MPU 以及两种执行模式来构建：特权 handler/thread 模式和非特权 thread 模式，特权入口通过 SVC 指令实现。通用系统中的 hypervisor 以更高的 CPU 特权级运行以隔离 guest OS；在这里，一个 supervisor 在单片机规模上扮演类似角色。</div>

<p class="news-summary">一项新规范提出一种标准 DNS 记录，让域名所有者可以公开标示域名正在出售。当域名不再出售时移除该记录；“不出售”只能通过没有该记录来表示。 这可能让域名出售意图变得机器可读、易于发现，进而影响域名投机、商标仲裁以及买家寻找域名的方式。它还可能引发法律问题，例如公开标示“在售”是否会在商标纠纷中对域名所有者不利。 该规范明确指出，没有该记录并不代表域名不出售，因为目前大多数在售域名并没有这一记录。它还指出“在售”标记没有相反值，因此唯一表示“不出售”的方式就是移除该记录。</p>
<div class="news-background"><strong>背景</strong> 域名系统（DNS）利用资源记录（如 A、MX、CNAME 记录）将域名映射到 IP 地址、邮件服务器等数据。新增一种“在售”记录类型，将在 DNS 内部为域名所有者提供一种标准化的方式来发布出售意向，使其可被自动化工具和服务发现。</div>

<h2 class="news-title"><a href="https://yogthos.net/posts/2026-08-07-portable-jolt.html">Jolt 新增程序镜像与可移植 Scheme 后端</a><span class="score-badge score-mid">7.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Aug 8, 14:12</span></div>
<p class="news-summary">Jolt 最近新增了两项特性：以 Common Lisp 和 Smalltalk 风格进行程序镜像序列化，以及一个与 Chez 运行时解耦的可移植 Scheme 层。这两者使得运行中的 Clojure 程序能够被保存、传输，并在不同的 Scheme 后端上重新加载。 这打破了程序与其启动进程或运行时之间的耦合，能够精确重现状态以进行事后调试和协作式 bug 报告。它还让同一份 Clojure 代码可以面向多种 Scheme 实现，在服务器、浏览器中运行，或编译为小型静态二进制文件。 镜像 API 提供 dump-world! 用于捕获完整世界状态，以及默认严格的 dump!，后者会报告任何不可序列化对象的路径；读取时会校验镜像头，以拒绝来自不兼容构建的过期数据。可移植 Scheme 层面向 Gambit 和 Stalin 血统的整程序优化编译器，且由于种子已在 Chez 上生成，这些后端无需提供运行时 eval。</p>
<div class="news-background"><strong>背景</strong> Jolt 是一个将 Clojure 代码编译为 Scheme 的 Clojure 实现，主要运行时为 Chez Scheme。程序镜像（program image）是运行中程序完整状态的序列化快照，这一技术长期被 Common Lisp 和 Smalltalk 系统用于保存和恢复会话。Chez Scheme 是一款成熟的 Scheme 实现，带有增量式原生代码编译器，并支持多种处理器后端。让 Jolt 与 Chez 解耦后，其输出无需修改源码即可在其他 Scheme 实现上运行。</div>

<h2 class="news-title"><a href="https://revisionprompting.info/">修订提示（Revision Prompting）降低工业 LLM 的时间与成本</a><span class="score-badge score-mid">7.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Aug 8, 20:20</span></div>
<p class="news-summary">Revision Prompting 是一种新技术，它根据输入的变化修订之前的 LLM 输出，而不是从头重新运行完整指令。作者称，在他们自己的工业提示场景中，大约节省了 80%的时间和 65%的成本。 该技术解决了生产级 LLM 工作流中朴素重新运行的两大缺点：由非确定性生成导致的输出不一致，以及重新生成完整输出的高时间/令牌成本。它能使自动化 LLM 流水线更加高效和一致，特别是在批量翻译、数据抽取和文档处理等场景中。 该方法将原始输出重新输入到提示中，让 LLM 生成输出补丁（OutputPatch），可根据指令选择使用 POSIX diff 或 JSON Patch（RFC 6902）等通用格式。由于大部分 token 从输出侧转移到输入侧，处理时间随之缩短，输出 token 成本也转换为更便宜的输入 token 成本；如果在几分钟内进行修订，提示缓存还能进一步降低输入成本。</p>
<div class="news-background"><strong>背景</strong> 工业提示（Industrial prompting）是指在自动化流程中重复使用同一指令，例如从发票中提取结构化数据或在发布期间翻译文档。由于 LLM 具有非确定性，对略有变化的输入重新生成完整输出可能引入不一致并产生完整处理成本。Revision Prompting 通过使用 diff 描述输入变化并要求 LLM 仅生成现有输出的补丁来避免这种情况。</div>

<p class="news-summary">一个新的开放参考文档——Brent Saner 的 ssharef.dev『OpenSSH 密钥结构指南』——以远超官方 PROTOCOL.key 的详细程度记录了 OpenSSH 密钥格式。它涵盖了 7.8 之前的传统 PEM 编码，并对较新的 &#x27;openssh-key-v1&#x27; 私钥结构进行了逐字段解析。 OpenSSH 密钥无处不在，但官方 PROTOCOL.key 内容简略且难以理解，开发者不得不对二进制格式进行逆向工程。这份指南为开发者和安全研究人员提供了清晰、完整的参考，减少了在构建密钥解析器、转换工具或安全工具时的猜测和潜在解析错误。 该指南展示了 v1 私钥包含可定制的 KDF 和加密算法、内嵌注释、对应的公钥以及用于完整性校验的四字节检查值。它完整剖析了二进制布局，包括带 null 终止符的 &#x27;openssh-key-v1&#x27; 头部、加密算法与 KDF 名称字符串、包含盐和工作因子的 KDF 选项，以及一个以填充字节结尾的已解密 ed25519 示例。</p>
