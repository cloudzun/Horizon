<h2 class="news-title"><a href="https://openai.com/index/building-scientific-understanding-with-academic-communities/">OpenAI 声称 AI 协助取得 Kakeya、ETH 反证与 Yang–Mills 成果</a><span class="score-badge score-high">10.0</span></h2>
<div class="news-meta"><span class="source-chip chip-hackernews">hackernews</span><span class="source-name">jonluca</span><span class="news-time">Oct 26, 21:35</span></div>
<p class="news-summary">OpenAI 发布了一篇题为《Working with academic communities to build scientific understanding》的文章，宣布借助其模型取得三项发现：调和分析中的 local smoothing / Kakeya 猜想结果、复杂度理论中对 Exponential Time Hypothesis（ETH）的反证，以及量子色动力学（QCD）的存在性证明和标准模型的完备化。据一位评论者引用公告原文，模型于 2026 年 9 月 9 日给出 Yang–Mills 存在性的自然语言证明，9 月 18 日给出 QCD 的证明，并推迟发布直至 2026 年 10 月 16 日完成 Yang–Mills 存在性的 Lean 形式化。 这三项声明中的任何一项都堪称里程碑式成果：Yang–Mills 存在性与质量间隙是克雷数学研究所的千禧年大奖难题之一，ETH 支撑了参数化复杂度中大量条件性下界，而 Kakeya 型估计则处于调和分析以及 restriction / local smoothing 猜想的中心地带。如果这些结果能经受独立审查，它们也将是 AI 系统能够参与前沿数学研究、而非仅限常规或计算性任务的有力信号。 目前可得的证据只有一篇公告页面和社区评论，并没有提供独立验证或同行评审，因此这三项声明都应视为未经验证；文中只提到对 Yang–Mills 存在性证明做了 Lean 形式化。要反证 ETH，需要给出一个在次指数时间内求解 3-CNF 可满足性问题的算法，而正如评论者指出的，推翻 ETH 本身并不意味着 P=NP 成立。</p>
<div class="news-background"><strong>背景</strong> Kakeya 问题问的是：一个在每个方向上都包含单位线段的集合最小能有多小，其各种变体与波动方程的 restriction 猜想和 local smoothing 猜想紧密相关。Exponential Time Hypothesis 由 Impagliazzo 和 Paturi 提出，是一个尚未证明的假设，认为 3-CNF 布尔可满足性问题无法在次指数时间内求解，它被广泛用作各类困难性结果的基础。Yang–Mills 存在性与质量间隙问题是七个千禧年大奖难题之一，奖金 100 万美元，要求严格构造出具有质量间隙的四维量子 Yang–Mills 理论；而作为强相互作用 Yang–Mills 理论的 QCD，其色禁闭至今仍未被证明。</div>

<h2 class="news-title"><a href="https://github.com/openai/math/blob/main/preprints/The-Exponential-Time-Hypothesis-is-False-October-25-2026/paper.pdf">预印本声称推翻指数时间假说</a><span class="score-badge score-mid">8.0</span></h2>
<div class="news-meta"><span class="source-chip chip-hackernews">hackernews</span><span class="source-name">vok</span><span class="news-time">Oct 26, 21:59</span></div>
<p class="news-summary">一篇题为《The Exponential Time Hypothesis Is False》的预印本已在 OpenAI 的公开数学仓库中发布，声称推翻了指数时间假说（ETH）。该文尚未经过验证，讨论主要集中在这一声称的结果能说明什么、不能说明什么。 如果正确，推翻 ETH 将是理论计算机科学的一项重大成果，因为 ETH 是细粒度复杂性中许多条件下界的基础。它将迫使研究者重新审视关于 3-SAT 及相关问题指数难度的假设，但该声称仍未经证实。 评论者指出了一个重要限制：形如 2^o(n) 的运行时间界在一般多项式时间归约下不会传递，要推出一般 NP 问题的次指数算法，需要 2^{n^o(1)} 形式的界。讨论还提出了关于实际 SAT 求解、SETH 影响以及该结果是否有直接算法应用的问题。</p>
<div class="news-background"><strong>背景</strong> 指数时间假说由 Impagliazzo 和 Paturi 于 1999 年提出，是一个未经证明的硬度假设，认为 3-SAT 无法在次指数时间内求解，即无法在 2^{o(n)} 时间内求解。SAT 是典型的 NP 完全问题：Cook–Levin 定理表明，NP 中的任何问题都可以在多项式时间内归约到 SAT。ETH 及其更强变体 SETH 被广泛用于推导计算机科学中各类算法的条件下界。</div>

<p class="news-summary">Ben Joffe 发表文章，提出了一种在除数为编译期常量时计算有符号 64 位向下取整除法的新方法：用高位乘法加上一次“add back”修正来实现，并给出了除以 86400 的具体示例。文中还按除数给出了在 ARM64 芯片（MacBook Pro M4 Pro、Snapdragon X1-26-100）和 x86 芯片（AMD Ryzen 9 9950X3D、2016 款 MacBook Pro 上的 Intel Core i7）上的吞吐量与延迟基准测试，认为向下取整除法可以比大多数语言的内置方法快得多。 向下取整除法（向 −∞ 舍入而非向 0 舍入）是许多程序员在处理负数时真正想要的语义，但通常要靠较慢的库函数调用，或在截断除法之上再加一次修正来实现。更廉价的常量除法方案对编译器开发者和底层系统工程师很有价值，作者还指出它同时可用于更快的正模运算以及更快的“欧几里得”除法（在除数为负时与向下取整除法不同）。 86400 的示例使用 64 位常量 A = −4454547087429121353（即 2^80/86400 + 1 − 2^64）和 B = 0x6117 &lt;&lt; 48，先计算 128 位乘积，再返回 (h + x) &gt;&gt; 16，其中对 x 的“add back”用于修正负乘数。作者指出这在 x86 上编译结果相当不错，因为 add-back 只需几条指令（adc），但在 ARM64 上要付出两次乘法的代价（mul 和 smulh），因为 ARM64 需要为高、低两个 64 位半结果分别做乘法；该方法适用于所有位宽，收益最大的是 64 位场景。</p>
<div class="news-background"><strong>背景</strong> Hacker&#x27;s Delight 是 Henry S. <h2 class="news-title"><a href="https://support.apple.com/en-us/149555">Apple 在 macOS 上封禁遭泄露的 eMudhra 中间 CA 证书</a><span class="score-badge score-mid">7.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Oct 26, 09:58</span></div>
<p class="news-summary">Apple 发布支持公告称，自 2026 年 10 月 19 日起，它已开始封禁遭泄露的 eMudhra 中间证书颁发机构（CA）所签发的 TLS 证书，并正在对该封禁进行进一步更新。Safari、Mail 以及使用 Apple 网络与安全框架的 App 现在会自动拒绝这些证书；而依赖命令行工具的 Mac 管理员和开发者，可以选择从 /etc/ssl/cert.pem 中移除相应的根 CA 证书，从而在未来的软件更新到来之前，阻止 curl、git 等工具接受这些证书。 由于中间 CA 私钥泄露会让攻击者签发看似对任意网站都有效的证书，这是一个信任锚层面的问题，影响所有 macOS 用户，而不仅仅是安全专家。该公告还暴露出 macOS 自身的一处缺口：基于静态 /etc/ssl/cert.pem 证书包进行校验的工具不会遵循 Apple 的证书封禁或吊销检查，因此开发者工作站和 CI 系统的管理员若想立刻获得防护，必须手动采取操作。 共有八个 eMudhra 中间 CA 的私钥遭到泄露：其中两个用于签发代码签名证书（Apple 的框架并不信任此类证书），另外六个用于签发 TLS 证书，每个 CA 各有两张证书，合计 12 个受影响条目，其证书链指向 emSign、AAA Certificate Services 等根证书。手动修复方案是从 /etc/ssl/cert.pem 中移除相关根 CA 证书，这会影响所有使用该文件的工具，并可能导致某些无关网站无法通过校验——这些网站的证书是经由未受影响的中间 CA 链到同一批根证书的；后续的 macOS 软件更新可能会覆盖该文件，因此在官方修复发布前，每次系统更新后都可能需要重复执行这些步骤。</p>
<div class="news-background"><strong>背景</strong> 公钥基础设施依赖一条信任链：根证书颁发机构是最终的信任锚，中间（下级）CA 代表根 CA 签发终端实体证书，从而让根 CA 的私钥可以离线保存。浏览器和操作系统只有在证书能够链到某个已受信任的根证书时才会信任它，这正是中间 CA 密钥失窃如此严重的原因——攻击者可以为任意域名签发仍能通过校验的证书，从而实施中间人拦截。Apple 的公告指出，macOS 上的 curl、git、python3、ruby、perl、openssl 等命令行工具是基于 /etc/ssl/cert.pem 这一静态证书包进行校验的，而不是走 Apple 的实时信任评估，因此上述封禁不会自动作用于这些工具。</div>

<h2 class="news-title"><a href="https://yossarian.net/til/post/posix-wordexp-3-is-dangerous/">POSIX wordexp(3) 的 WRDE_NOCMD 保护并不可靠</a><span class="score-badge score-mid">7.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Oct 25, 15:09</span></div>
<p class="news-summary">yossarian.net 的一篇技术文章指出，在某些 libc 实现中，即使设置了 WRDE_NOCMD，POSIX wordexp(3) 仍可能执行命令替换。文章特别点名 musl，并提到 macOS 的 wordexp helper 在 2023 年也存在同样的绕过。 开发者常把 wordexp(3) 用于波浪号展开，并可能误以为 WRDE_NOCMD 能让不可信输入变安全；这一发现打破了该假设，会把看似无害的路径展开变成潜在的命令注入入口。这对处理用户可控字符串的 C 和系统软件开发者尤其重要。 musl 通过委托系统 shell 来实现 wordexp(3)，只做粗略的命令替换扫描，因而漏掉 GNU Bash 视为合法命令替换的某些模式。macOS 则委托给 /usr/lib/system/wordexp-helper，作者没有测试在默认 shell 改为 zsh 后该绕过是否仍然有效。</p>
<div class="news-background"><strong>背景</strong> wordexp(3) 是 POSIX 定义的 C 语言 API，用于对字符串执行 shell 风格的单词展开，包括波浪号、变量和命令替换。它常被推荐用来把 ~/foo 这类路径展开成 /home/me/foo。flags 参数决定允许哪些展开：传 0 会启用包括命令替换在内的全部功能，而 WRDE_NOCMD 的本意是拒绝命令替换。不同 libc 对该 API 的实现方式并不相同，这也正是问题的来源。</div>

<h2 class="news-title"><a href="https://turtleware.eu/posts/Heavenly-delights-of-hashing-numbers-under-EQUALP.html">ECL 实现者理清 EQUALP 下数字哈希的一致性问题</a><span class="score-badge score-mid">7.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Oct 26, 15:40</span></div>
<p class="news-summary">一位 ECL（Embeddable Common Lisp）实现者发表了详细的技术札记，讲述他为了优化基于表的泛型函数分派，最终不得不重写 ECL 的哈希表与哈希函数，其中最核心的是让数字在谓词 #&#x27;EQUALP 下的哈希保持一致。文章从简单的基础模型出发，经过改进版本，最终提炼出一个优雅的概念模型；进行中的代码位于仓库的 xxhash、swiss-ht 和 improve-gf-cache 分支，后续版本会带来这些改进。 哈希表的正确性取决于哈希函数与表的相等性判定保持一致，因此任何 EQUALP 相等的对象必须得到相同的哈希值；修复这一点消除了 ECL 中一类隐蔽的缺陷，而随附的基准测试（槽访问、随机键下的 EQUALP 查找、插入/删除循环、短字符串）也指向哈希表与泛型函数分派将显著提速。受众局限于 Lisp 实现者与语言运行时工程师，但结果会影响所有嵌入 ECL 或依赖 CLOS 分派性能的人。 实现中，fixnum 只需对单个机器字做哈希，bignum 则对符号位与 limb 数组一起哈希；对于二进制浮点表示（dyadic），实现会用一个线程局部的暂存寄存器提取尾数（在 x86-64 上 long double 的尾数为 64 位），从而避免不必要地 cons 出 bignum；当有理数不是二进制可表示时，还会分别哈希其分子与分母。文中明确假设浮点为二进制表示（float radix 为 2），这也是 ECL 采用的表示；作者还说明，这项调查源于他想衡量新的基于表的分派究竟快多少或慢多少。</p>
<div class="news-background"><strong>背景</strong> Common Lisp 有多种语义不同的相等性谓词，EQUALP 是较为宽松的一个：它在比较数字时忽略类型（因此 3 与 3.0 在 EQUALP 下相等），字符串比较不区分大小写，并会递归比较向量与 cons。Common Lisp 的哈希表以这类谓词作为测试参数，因此必须配一个与之匹配的哈希函数——在测试下相等的对象必须产生相同的哈希值，否则查找会悄无声息地失败。对数字而言这很棘手，因为数值塔混合了 fixnum、bignum、有理数与浮点数，像 2、2/1 和 2.0 这样的值必须哈希一致。ECL 是一个小型的 ANSI Common Lisp 实现，支持 CLOS，可编译为 C 并嵌入 C 程序，因此其内部哈希表同时支撑用户哈希表与 CLOS 方法分派。</div>

<h2 class="news-title"><a href="https://atgreen.github.io/repl-yell/posts/openldk-java-in-common-lisp/">OpenLDK 将 Java 运行时与 JIT 带入基于 SBCL 的 Common Lisp</a><span class="score-badge score-mid">7.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Oct 26, 06:15</span></div>
<p class="news-summary">一位曾参与 gcj（GNU Compiler for Java）的开发者发布了 OpenLDK：一个用 Common Lisp 编写的 Java JIT 编译器与运行时，它读取 Java 字节码、将其翻译成 Lisp，再由 SBCL 把这段 Lisp 编译为原生机器码。作者表示近期在运行 JVM 之上的语言和 Spring Boot 应用方面取得进展，其中包括把已初始化的 Spring Boot 应用保存进 Lisp 镜像，并在约 84 毫秒内重新启动。 该项目表明 Java 对象可以与 Lisp 应用处于同一进程和同一堆中，从而实现一些不寻常的多语言组合：Java 类变成 CLOS 类、Java 自身的编译器在 SBCL 内运行、以及在 Java 或 Kotlin 方法周围添加 Lisp 方法。其影响主要集中在 Common Lisp 与 JVM 实现社区，而非通用软件开发领域。 作者明确表示，在通用 Java 执行场景下 HotSpot 会快得多；在一项 Spring Boot 启动基准测试中，GraalVM Native Image 更快也更小，为 53.5 毫秒、41 MB，而 OpenLDK 为 83.9 毫秒、175 MB。与 GraalVM 的封闭世界（closed-world）假设不同，OpenLDK 保留了类加载器和 JIT，因此启动后仍可编译新类；但它仍有兼容性缺口，包括尚未实现字节码校验，仅面向 Linux 上的 SBCL，且保存的镜像在运行时需要 classpath 文件和 JDK。</p>
<div class="news-background"><strong>背景</strong> Common Lisp 是经 ANSI 标准化的 Lisp 方言，而 SBCL（Steel Bank Common Lisp）是一个自由开源的实现，以其高性能原生编译器著称——OpenLDK 正是依赖它把翻译后的 Lisp 代码编译为机器码。JVM 通常在 HotSpot 之类的虚拟机中执行 Java 字节码，而 gcj 是一个现已停止维护的 GNU 项目，能把 Java 编译为字节码或原生机器码。OpenLDK 延续了这一脉络但另辟蹊径：它不是一个独立虚拟机，而是把 Java 执行直接嵌入到运行中的 Lisp 进程里。</div>
