<h2 class="news-title"><a href="https://z.ai/blog/glm-5.3">智谱发布 GLM-5.3：具备涌现网络能力的先锋编程模型</a><span class="score-badge score-high">9.0</span></h2>
<div class="news-meta"><span class="source-chip chip-hackernews">hackernews</span><span class="source-name">pella</span><span class="news-time">Aug 14, 05:19</span></div>
<p class="news-summary">2026 年 8 月 14 日，中国 AI 公司智谱（Z.ai）正式发布 GLM-5.3，这是一个 743B 参数的开源权重模型，在 CyberGym 和 AutomationBench 等网络安全基准测试中位居榜首。该模型在真实红队场景中展示了自动漏洞发现能力，包括 WordPress 插件中的 0day 漏洞利用及 6.8 内核漏洞利用的适配。 GLM-5.3 的涌现网络能力标志着 AI 驱动安全研究的新时代，模型可以大规模自主发现并利用漏洞。这加剧了中西前沿实验室之间的竞争，并可能从根本上降低漏洞发现的成本、提升漏洞发现的节奏，影响整个软件生态系统。 开源权重将分阶段发布，并置于安全审查之后，目前可通过 GLM Coding Plan 立即访问。Z.ai 似乎还在大规模扫描开源及流行软件，并通过 cvd.z.ai 协调平台披露发现，其中许多 CVE 处于保密期，且被评定为严重或高危级别。</p>
<div class="news-background"><strong>背景</strong> GLM 是智谱（Z.ai）的开源权重大型语言模型系列；GLM-5.3 是 GLM-5.2 的继任者，定位为与 Anthropic 的 Mythos 5 等前沿模型竞争。涌现能力是指 AI 模型在跨越特定规模或复杂性阈值后出现的、意想不到的定性行为；而自动漏洞发现则是应用 AI 来系统性地识别安全弱点，例如软件缺陷和错误配置。</div>

<h2 class="news-title"><a href="https://arstechnica.com/security/2026/08/terabytes-of-credentials-leaked-in-massive-supply-chain-attack/">LiteLLM 供应链攻击泄露 TB 级凭据</a><span class="score-badge score-high">9.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Ars Technica AI</span><span class="news-time">Aug 12, 21:43</span></div>
<p class="news-summary">安全公司 CloudSEK 和 Hudson Rock 披露，针对开源 AI 工具 LiteLLM 的供应链攻击导致大量企业凭据泄露。攻击者在 3 月一个约 40 分钟的时间窗口内，从通过 PyPI 下载的受感染 LiteLLM 版本中窃取凭据；Hudson Rock 表示分析了包含这些数据的 195TB 文件。 这一事件表明，单一上游开源组件的沦陷可连锁导致数千家组织的数据暴露，包括 Microsoft、Amazon、Cisco 和 Samsung 等。Hudson Rock 的 Alon Gal 表示，此次攻击产生了超过 43 万个采集点，收集了数百万个秘密信息，标志着网络安全行业必须应对的供应链威胁已进入全新规模。 据 CloudSEK 称，泄露数据包括云密钥、代码仓库令牌、SSH 密钥、Kubernetes secrets、软件包发布凭据、环境变量和 AI 提供商密钥，可能影响超过 2500 家组织。LiteLLM 事件源于此前针对 Trivy 漏洞扫描器的供应链攻击；TeamPCP 黑客团伙声称对此负责，研究人员基本证实了这一说法。</p>
<div class="news-background"><strong>背景</strong> LiteLLM 是 BerriAI 开发的开源 Python SDK 和 AI 网关，允许开发者以 OpenAI 兼容格式调用 100 多个大语言模型 API。供应链攻击通过在合法软件包或其依赖项中植入恶意代码实施，因此所有安装被感染软件包的下游项目都会暴露风险。由于 LiteLLM 在 AI 开发中被广泛使用，短暂的入侵窗口也可能让机密信息快速扩散到众多组织。</div>

<h2 class="news-title"><a href="https://github.com/xoreaxeaxeax/skitter-creek-bath-salts">DRAM 加扰攻击解锁 CPU 隐藏功能</a><span class="score-badge score-high">9.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Aug 13, 16:06</span></div>
<p class="news-summary">安全研究员 Christopher Domas 发布了开源项目 skitter-creek-bath-salts，利用 DRAM 加扰重映射物理内存地址，进而暴露 AMD Family 16h CPU 上的受保护区域，包括平台安全处理器（PSP）、系统管理模式（SMM）、C6 DRAM 和微码。该研究计划在 Black Hat 2026 上以“Spaghettifying DRAM”为题进行展示。 该攻击绕过了依赖 DRAM 地址转换的硬件级安全原语，可能危及 AMD SEV、Intel SGX/TDX、ARM TrustZone 等机密计算技术。由于底层内存控制器转换管线广泛存在于 AMD、Intel、ARM 和 RISC-V 平台中，该技术可能对 CPU 安全产生广泛影响。 演示中利用的是 AMD Family 16h 上的单个配置寄存器，选择该型号是因为其数据手册记录了 DRAM 控制器的转换寄存器，并显示这些寄存器无法被锁定；而更新的型号则省略了这些信息。项目包含完整工具链——dram_state、dram_carveouts、dram_alias，以及 gather_aliases.py/unspaghettify.py 分析管线，并在 USAGE.md 中提供了示例和说明。</p>
<div class="news-background"><strong>背景</strong> DRAM 加扰是一种内存控制器技术，用于重排或混淆物理地址与实际 DRAM 单元之间的映射，通常用于缓解侧信道攻击。AMD 平台安全处理器（PSP）是芯片上独立的隔离安全处理器，负责信任链、证明以及安全加密虚拟化（SEV）等安全功能。系统管理模式（SMM）是一种高权限的 CPU 执行模式，通常供固件使用，其内存对操作系统通常不可见。通过改写 DRAM 控制器的地址重映射设置，该攻击“意大利面化”（spaghettify）了内存，从而破坏了这些安全机制所依赖的隔离假设。</div>

<div class="news-meta"><span class="source-chip chip-hackernews">hackernews</span><span class="source-name">erdaltoprak</span><span class="news-time">Aug 14, 15:00</span></div>
<p class="news-summary">Qwen 3.8 27B 已发布，这是一款拥有 270 亿参数的紧凑模型，据报道在某些基准测试中可与 Opus 4.6 和 Opus 4.7 Max 等更大模型持平甚至胜出。该模型设计为可在笔记本电脑等本地硬件上高效运行，Hugging Face 上还提供 FP8 量化版本。 这一发布凸显了紧凑模型如今可与更大、更昂贵的系统竞争，可能重塑开发者和企业部署 AI 的方式，以降低成本与延迟。它也强化了 AI 竞赛的叙事，因为据报道一款中国小型模型的性能已接近美国旗舰模型。 社区成员报告了令人印象深刻的实际结果，包括 Qwen 3.8 27B 在 DeepSWE 基准测试中得分 42.2，而 Opus 4.7 Max 配合 Claude Code 得分为 40，不过 GSM8K 等某些基准测试仅在极小的样本上运行。用户还指出 FP8 版本可在 M5 Max Mac 等笔记本电脑上运行，部分人表示期待未来推出 MoE（混合专家）变体。</p>

<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Aug 13, 17:43</span></div>
<p class="news-summary">Domen Kožar 提议为 Rust 引入一个新的 FFI ABI——extern &quot;fil-c&quot;，让 Rust 能够安全地调用经内存安全工具链 Fil-C 重新编译的 C/C++ 库。文中还提到 Zig 的 Andrew Kelley 已提出一个受 Fil-C 启发的类似 ABI，并邀请各社区在 OceanSprint 上进行合作。 这可能改变在 Rust 中使用遗留 C 代码的成本结构：用 Rust 重写热点路径可以让运行时安全检查消失，而保留 C 库则能保持内存安全但代价是性能降低。同时，这也为 Rust、Zig、Fil-C 和 Nix 社区在共享内存安全 ABI 上达成一致铺平了道路。 Fil-C 与 C 源代码兼容，但刻意不保持 ABI 兼容，普通 Rust 的 extern &quot;C&quot; 实际使用的是 Fil-C 所称的 &quot;Yolo-C&quot; ABI。提议的桥梁将先从标量、复制的字符串和切片、不透明句柄开始，不提供退回不安全 C 的逃生通道；filnix 已为 Nix 打包 Fil-C，并移植了 100 多个 nixpkgs 包。</p>
<div class="news-background"><strong>背景</strong> Rust 的 C FFI 依赖 unsafe 块，因为 Rust 和 C 都无法在边界处强制内存安全契约。Fil-C 是 C 和 C++ 的一种内存安全实现，它通过运行时检查和并发垃圾回收器重新编译代码，使内存安全违规变成 panic 而不是可被利用的漏洞。与 AddressSanitizer 等 sanitizer 不同，Fil-C 的保护机制无法被攻击者绕过。</div>

<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Aug 14, 19:12</span></div>
<p class="news-summary">一位资深嵌入式开发者发表详细批评文章，认为 RISC-V 的“开放规范”地位并不能保证免费实现，且其高度可选的架构损害了实用性。作者称 RISC-V 将凭借设计之外的因素赢得低端微控制器市场，但在桌面与高端计算领域不太可能取代 ARM。 这很重要，因为它挑战了“RISC-V 的开放性必然带来更优秀且免费可得的 CPU 设计”这一普遍假设。资深嵌入式开发者的批评可能影响微控制器、单板计算机和高性能计算领域的采纳决策，而 RISC-V 倡导者正承诺在这些领域占据主导。 关键技术点包括：RISC-V 可选的 Supervisor 模式和 CSR 使特权级检测和陷阱处理变得脆弱；作者还指出开放规范并不会凭空产生免费的高性能乱序执行核心。作者认为低端与高端 CPU 的需求在架构上截然对立。</p>
<div class="news-background"><strong>背景</strong> RISC-V 是在加州大学伯克利分校开发的一种开放指令集架构（ISA），包含一个小型基础整数指令集和众多可选扩展。它定义了三个主要特权级——Machine（M）、Supervisor（S）和 User（U）——以及一组控制和状态寄存器（CSR），如 misa 和 sepc，但规范中许多功能都是可选的。这种可选性旨在让实现变得简单廉价，但也可能给系统软件的移植性和陷阱处理带来挑战。</div>

<h2 class="news-title"><a href="https://sebsite.pw/w/20260801-pythonconstants.html">Python 预声明常量的行为不一致</a><span class="score-badge score-mid">7.0</span></h2>
<div class="news-meta"><span class="source-chip chip-rss">rss</span><span class="source-name">Lobsters</span><span class="news-time">Aug 13, 05:28</span></div>
<p class="news-summary">Sebsite 的技术分析指出，Python 的六个预声明常量行为并不一致：True、False、None 是保留关键字，__debug__ 是不可赋值的标识符，而 Ellipsis 和 NotImplemented 可以在 builtins 模块中被重新赋值，且不影响 ... 字面量的值。它还演示了 setattr(builtins, &#x27;True&#x27;, 67) 会改变 builtins 属性，但不会改变 True 记号本身的值。 这些微妙的语义差异对语言设计者、编译器实现者以及依赖 Ellipsis 或 NotImplemented 等常量的高级 Python 开发者都很重要。厘清真正的常量与普通 builtins 名称之间的区别，有助于理解 Python 的名称解析和优化行为，例如 -O 选项对 __debug__ 的影响。 True、False、None 是词法记号，因此 x.True 这样的表达式会引发 SyntaxError；__debug__ 即使作为属性名也无法被赋值。对 builtins.Ellipsis 赋值会改变 Ellipsis 名称，但不会改变 ... 字面量的值；而 setattr(builtins, &#x27;__debug__&#x27;, 67) 也不会改变裸 __debug__ 的值。</p>
<div class="news-background"><strong>背景</strong> Python 的内置常量定义在 builtins 模块中；官方文档指出，None、False、True 和 __debug__ 不可重新赋值，因此可以被视为真正的常量。Ellipsis（即 ... 或 Ellipsis）是用于占位的内置对象，但由于它只是一个普通的内置名称，所以可以被重新赋值，而 ... 字面量始终解析为 Ellipsis。__debug__ 常量反映了 Python 是否以 -O 优化选项启动。</div>
